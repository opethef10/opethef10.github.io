> Localias maps memorable domain names to local ports. No more remembering that your React app is on :3000 and Django app on :8001

You decide to develop a website using a well-known web framework such as Django. Or you want to serve a bunch of static files over a directory. Or you would like to develop an app where front-end and back-end are run separately. At first, it is easy, you type a command like this:

```bash
python -m http.server
```

This command serves the contents of the current directory and you can reach it in your browser from the address [localhost:8000](http://localhost:8000). It works! Your computer serves a website and you can access to it from your own browser. Then you decide to run a Django server with this command:

```bash
python manage.py runserver
```

Just like Python's http server, Django server also uses the port 8000 as default. This will create an error and we need to choose another port for Django app. Luckily we can choose the port number using this command:

```bash
python manage.py runserver 8001
```

Now you can reach the Django app from the address [localhost:8001](http://localhost:8001). And then you have another app, you serve it from the port 8002. You may have a React app that is served from the port 3000 and it has the backend app at the port 8003. This can go on and on. Soon, remembering all of these port numbers become a problem.

Sure, you could use a reverse proxy or manually edit your host file, but [Localias](https://github.com/peterldowns/localias) gives you a convenient way to manage your local websites. For installation and the complete configuration, follow the instructions in the Localias repository. We'll dive directly to the core feature of Localias.

```bash
localias add python.local 8000
```

And done! Localias created an alias for your port 8000 and now you can type in your browser [python.local](http://python.local) and it takes you to the python http server.

Now let's add more aliases:

```bash
localias add django.local 8001
```

Now you can go to [django.local](https://django.local). Localias provides a TLS certificate, so you can test your website in HTTPS. And you're not even limited to `blabla.local` format. Let's add one more time:

```bash
localias add frontend.myapp.local 3000
localias add backend.myapp.local 8002
```

You can serve frontend and backend of the same app under same local domain. You aren't even limited to local TLD here. You can use anything you want, `test`, `tld`, `mydomain` etc. It's recommended to use something that wouldn't clash with real TLDs.

However, `local` suffix has one significant advantage. Thanks to mDNS technology, someone using the same LAN or Wi-Fi network can connect to your local website. Or you can serve your website from your computer and connect to it from your phone's browser to see if it looks good in mobile browsers.

I apply this convention to every project I create. Even the ones that meant for quick testing or private experiments. But the main advantage comes from the ease of mapping my local URLs to production URLs. For instance, this blog is served at [blog.onurarikan.dev](https://blog.onurarikan.dev) and the local alias is `blog.onurarikan.local`. The names mirror each other, so there's no mental mapping. I just append `.local` and I'm in the local development environment. It keeps production and local separate while making both easy to remember. That's the real value of aliases: they remove small recurring frictions from your workflow, freeing you to focus on what you're actually building.
